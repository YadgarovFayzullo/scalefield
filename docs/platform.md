# Scalefield — платформа вместо Vercel + Supabase

Scalefield — панель и control-plane для проектов, которые живут на своих
серверах: деплой из Git, домены и TLS, база данных, хранилище, метрики и
логи в одном месте. Первый клиент и полигон — researcher.uz; всё, что
делается для него, делается сразу как функция платформы, а не как костыль.

Документ — «почва»: что уже есть, какая модель, куда идём и какие решения
не пересматриваем. Обновлять при каждом шаге дорожной карты.

## 1. Что есть сегодня (сентябрь 2026)

| Слой | Реализация | Где |
|---|---|---|
| Control-plane | Next.js 16 route handlers + Drizzle + Postgres (`scalefield`) | `src/db`, `src/lib/projects.ts`, `src/app/api/projects/*` |
| Панель | Next.js 16, shadcn/ui, recharts; проекты → `/p/<slug>/…` | `src/app/dashboard`, `src/app/p/[project]` |
| Агент сервера | FastAPI: psutil, docker.sock, `pg_stat_*`, JSON access-log Traefik; деплой сервисов через `docker compose` | `agent/` (бывший `researcher-uz-status/api`) |
| Деплой | GitHub Actions собирает образ и грузит его на сервер по SSH, `docker compose up` | `.github/workflows/ci.yml` в репо researcher-uz |
| Маршрутизация и TLS | Traefik с Let's Encrypt, сеть `edge` | `/opt/apps/traefik` на сервере |
| База проекта | Postgres 17 (pgvector) в контейнере, бэкап ночью в R2 | `/opt/apps/backend`, бакет `researcher-backup` |
| Хранилище | Cloudflare R2 (`researcher-files`, публичный r2.dev-хост) | бэкенд researcher.uz |
| Вход | один пароль владельца (`DASHBOARD_PASSWORD`), cookie-сессия | `src/lib/session.ts`, `src/proxy.ts` |

Панель уже показывает только реальные данные: статус сервера и контейнеров,
Postgres (размер, соединения, медленные запросы), трафик по access-логу,
деплои из GitHub Actions, контентные метрики проекта.

## 2. Доменная модель

Схема control-plane (`src/db/schema.ts`), ориентир — Vercel (Team → Project →
Deployment → Domain) и Supabase (Organization → Project → Database/Storage).

```
organizations ─┬─ memberships ── users
               ├─ servers   (хост + агент: agent_url, agent_token_enc)
               └─ projects  (slug, server_id, settings)
                    ├─ services    (контейнер, repo, workflow, port) ── domains
                    ├─ deployments (source: github_actions | scalefield)
                    ├─ databases   (engine, container, url_enc)
                    └─ buckets     (r2 | s3, credentials_enc)
```

Правила:
- Секреты только в полях `*_enc`, шифруются `src/lib/secrets.ts`
  (AES-256-GCM, ключ `ENCRYPTION_KEY`). В браузер токены агентов и строки
  подключения не уходят никогда: клиент ходит в `/api/projects/<slug>/…`,
  прокси подставляет их на сервере.
- Проект = единица владения и биллинга. Сервер может нести несколько
  проектов; сервис принадлежит ровно одному проекту.
- Деплой — запись в `deployments` независимо от того, кто его сделал:
  сегодня их синхронизирует GitHub Actions, завтра будет писать свой билдер.
  Уникальность — `(source, external_id)`.
- `projects.settings` — JSONB для того, что не заслуживает колонки
  (например, `contentMetrics` включает ручку `/status/content` агента).

Бутстрап: при пустой базе первый проект создаётся из env
(`STATUS_API_URL`, `STATUS_API_TOKEN`, `GITHUB_REPOS`, `BOOTSTRAP_*`) —
чтобы существующая установка поднялась без ручного SQL. После этого env
не читается, источник истины — база.

## 3. Архитектура

```
 браузер ──► панель (Next.js) ──► control-plane API ──► Postgres `scalefield`
                                        │
                                        │ X-Status-Token (по проекту → серверу)
                                        ▼
                     сервер проекта: агент (FastAPI) ─┬─ docker.sock
                                                      ├─ pg_stat_* базы проекта
                                                      └─ access-log Traefik
                     Traefik (edge, TLS) ── контейнеры сервисов ── Postgres ── R2
```

- **Control-plane** — единственный, знает всё о проектах, хранит секреты,
  ходит к агентам. Панель и API в одном Next-приложении (как Studio у Supabase).
- **Агент** — один на сервер, не публичный (токен, внутренняя docker-сеть),
  ничего не решает сам: отдаёт метрики и, в следующей фазе, исполняет
  команды деплоя от control-plane.
- **Билдер** — сборка образов вне сервера проекта (GitHub Actions сейчас,
  отдельный builder-хост потом): сервер на 2 ГБ сборку Next не тянет,
  и это останется правдой для клиентских VPS.
- **Edge** — Traefik на каждом сервере: домены и сертификаты решаются
  лейблами контейнеров, control-plane лишь генерирует compose.

Чего сознательно НЕ делаем: serverless-функций, edge-рантайма, своего CDN,
глобальной репликации. Это не наша весовая категория; наша — «свой VPS,
но с опытом Vercel/Supabase».

## 4. Дорожная карта

Каждая фаза заканчивается тем, что researcher.uz живёт на ней в проде.

**Фаза 0 — панель на реальных данных.** Сделано 25.09.2026.

**Фаза 1 — control-plane и проекты.** В работе (эта ветка).
- [x] Схема и миграции, реестр проектов, шифрование секретов.
- [x] Маршруты `/p/<slug>/…`, переключатель проектов, деплои в базе.
- [ ] CRUD проектов/серверов/сервисов в панели (пока — SQL).
- [ ] Health агента: `servers.last_seen_at`, «сервер недоступен» в списке.
- Готово, когда второй проект (не researcher.uz) добавляется без правки кода.

**Фаза 2 — деплой из Git.**
- [x] Деплой через агента (25.09): `POST /deploy` пишет сервис в compose-стек
  `${APPS_ROOT}/<project>/docker-compose.yml` и делает `up -d --pull always`
  (`agent/app/deploy.py`, нужен docker CLI + compose-плагин в образе агента и
  том `/opt/apps`). Control-plane: сервисы с образом, портом, env (шифрованные),
  томами, доменами → лейблы Traefik + сеть `edge`; `/p/<slug>/services` —
  Deploy/Redeploy/Remove, лог в `deployments` (source = scalefield).
  Контейнер называется `<project>-<service>`; без доменов порт публикуется
  на 127.0.0.1 хоста.
- [x] Фоновые задачи агента с живым логом (25.09): `POST /jobs/deploy`,
  `POST /jobs/build`, `GET /jobs/<id>?since=` (`agent/app/jobs.py`); строка в
  `deployments` создаётся сразу как in_progress, `syncDeployment` подтягивает
  лог и результат, панель поллит раз в 2 с.
- [x] Rollback (25.09): `deployments.image` + `GET …/services/<id>/images` —
  список успешно задеплоенных образов, откат = деплой выбранного.
- [x] Сборка из Git (25.09): агент клонирует репозиторий (`git clone --depth 1
  --branch`), собирает `docker build` на том же хосте и деплоит образ
  `<project>/<service>:<ref>-<время>` без реестра (модель Dokku/Coolify).
  Webhook GitHub `POST /api/hooks/github/<serviceId>` с подписью
  `X-Hub-Signature-256` секретом сервиса; push в ветку при `autoDeploy` →
  сборка. Репозиторий — `owner/name` (GitHub, приватный через `GITHUB_TOKEN`)
  или полный git-URL.
- [ ] Билдер на отдельном хосте + реестр: сервер researcher.uz (2 ГБ) сборку
  Next не потянет; нужен `servers.role = builder`, `docker push` в реестр и
  деплой на целевой сервер.
- [ ] GitHub App вместо PAT + ручного webhook (одна кнопка «подключить репо»).
- Готово, когда researcher-uz деплоится кнопкой без CI-скрипта в репо
  (упирается в билдер-хост).

**Фаза 3 — базы данных.**
- [x] Редактор таблиц (25.09): список таблиц по схемам, страницы строк,
  сортировка, фильтр, правка ячеек, вставка и удаление строк —
  `/p/<slug>/tables`, `src/lib/project-db.ts`. Control-plane ходит в базу
  проекта напрямую по `databases.url_enc`; таблицы без PK и представления —
  только чтение.
- [ ] Провижининг Postgres на сервере проекта: контейнер, роль, пароль в
  `databases.url_enc`, пулер (PgBouncer/Supavisor), ночной бэкап в R2 и
  восстановление из панели.
- [x] SQL-редактор (25.09): `/p/<slug>/sql`, транзакция READ ONLY по
  умолчанию (запись — явным тумблером), таймаут 30 с, до 1000 строк в ответе,
  история в localStorage, CSV результата.
- [x] Правка схемы (25.09): колонки (добавить, переименовать, тип, NULL,
  default, удалить), индексы, создание и удаление таблиц — `src/lib/project-schema.ts`.
  Имена по маске + `qi()`, типы через `::regtype`, default — сырое выражение.
- [x] Экспорт CSV таблицы потоком `COPY … TO STDOUT` с текущим фильтром и сортировкой.
- Готово, когда база researcher.uz заведена через панель, а бэкап-скрипт
  на сервере заменён агентом.

**Фаза 4 — хранилище и домены.**
- Бакеты R2/S3 на проект (создание, ключи, публичные ссылки), обозреватель.
- Домены через панель: запись в `domains` → лейблы Traefik → сертификат;
  проверка DNS и статус TLS.

**Фаза 5 — мультитенантность.**
- Регистрация, организации, роли (`users`, `memberships` уже в схеме),
  API-токены, аудит действий, лимиты и биллинг.
- Подключение чужого сервера: скрипт установки агента одной командой.

## 5. Решения, которые не пересматриваем

- **Никаких мок-данных.** Если метрики нет — панель говорит «не настроено».
- **Образы не собираются на сервере проекта.**
- **Одна база control-plane, одна таблица деплоев** для всех источников.
- **Агент только по токену и только из внутренней сети**; публичного
  порта у него нет.
- **Тяжёлое — за пределами сервера researcher.uz**: 2 vCPU / 2 ГБ, ML и
  сборки туда не ставить.
- **Стек не множим**: TypeScript для control-plane и панели, Python для
  агента (там живёт docker/psutil-код), Traefik для edge. Переписывать агент
  на Go имеет смысл только ради установки одним бинарником на чужие хосты.

## 6. Открытые вопросы (решает владелец)

1. Позиционирование и имя продукта: «Vercel + Supabase для своего VPS»
   или хостинг под ключ на наших серверах (тогда нужна фаза «пул серверов»).
2. Реестр образов: ghcr.io (бесплатно для публичных, лимиты для приватных)
   или свой registry на билдер-хосте.
3. Где живёт билдер: GitHub Actions (бесплатные минуты, чужая инфра) или
   свой раннер на отдельном сервере.
4. Первый внешний клиент: демо-журналы researcher.uz как отдельные проекты
   или другой продукт владельца (QRTifact, content-pilot).
