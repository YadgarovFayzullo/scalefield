# Scalefield — платформа вместо Vercel + Supabase

Scalefield — панель и control-plane для проектов, которые живут на своих
серверах: деплой из Git, домены и TLS, база данных, хранилище, метрики и
логи в одном месте. Первый клиент и полигон — researcher.uz; всё, что
делается для него, делается сразу как функция платформы, а не как костыль.

Документ — «почва»: что уже есть, какая модель, куда идём и какие решения
не пересматриваем. Обновлять при каждом шаге дорожной карты.

## 1. Что есть сегодня (сентябрь 2026)

| Слой | Реализация | Где |
|---|---|---|
| Control-plane | Next.js 16 route handlers + Drizzle + Postgres (`scalefield`) | `src/db`, `src/lib/projects.ts`, `src/app/api/projects/*` |
| Панель | Next.js 16, shadcn/ui, recharts; проекты → `/p/<slug>/…` | `src/app/dashboard`, `src/app/p/[project]` |
| Relay | Node + `ws`: держит WebSocket-соединения агентов, пересылает им запросы control-plane; в базу не ходит | `relay/server.ts`, `src/lib/relay.ts` |
| Агент сервера | FastAPI: psutil, docker.sock, `pg_stat_*`, JSON access-log Traefik; деплой сервисов через `docker compose`. Сам подключается к relay (обратный туннель), входящих портов нет | `agent/` (бывший `researcher-uz-status/api`), туннель — `agent/app/tunnel.py` |
| Деплой | GitHub Actions собирает образ и грузит его на сервер по SSH, `docker compose up` | `.github/workflows/ci.yml` в репо researcher-uz |
| Маршрутизация и TLS | Traefik с Let's Encrypt, сеть `edge` | `/opt/apps/traefik` на сервере |
| База проекта | Postgres 17 (pgvector) в контейнере, бэкап ночью в R2 | `/opt/apps/backend`, бакет `researcher-backup` |
| Хранилище | Cloudflare R2 (`researcher-files`, публичный r2.dev-хост) | бэкенд researcher.uz |
| Вход | один пароль владельца (`DASHBOARD_PASSWORD`), cookie-сессия | `src/lib/session.ts`, `src/proxy.ts` |

Панель уже показывает только реальные данные: статус сервера и контейнеров,
Postgres (размер, соединения, медленные запросы), трафик по access-логу,
деплои из GitHub Actions, контентные метрики проекта.

## 2. Доменная модель

Схема control-plane (`src/db/schema.ts`), ориентир — Vercel (Team → Project →
Deployment → Domain) и Supabase (Organization → Project → Database/Storage).

```
organizations ─┬─ memberships ── users
               ├─ servers   (хост + агент: agent_url, agent_token_enc)
               └─ projects  (slug, server_id, settings)
                    ├─ services    (контейнер, repo, workflow, port) ── domains
                    ├─ deployments (source: github_actions | scalefield)
                    ├─ databases   (engine, container, url_enc)
                    └─ buckets     (r2 | s3, credentials_enc)
```

Правила:
- Секреты только в полях `*_enc`, шифруются `src/lib/secrets.ts`
  (AES-256-GCM, ключ `ENCRYPTION_KEY`). В браузер токены агентов и строки
  подключения не уходят никогда: клиент ходит в `/api/projects/<slug>/…`,
  прокси подставляет их на сервере.
- Проект = единица владения и биллинга. Сервер может нести несколько
  проектов; сервис принадлежит ровно одному проекту.
- Деплой — запись в `deployments` независимо от того, кто его сделал:
  сегодня их синхронизирует GitHub Actions, завтра будет писать свой билдер.
  Уникальность — `(source, external_id)`.
- `projects.settings` — JSONB для того, что не заслуживает колонки
  (например, `contentMetrics` включает ручку `/status/content` агента).

Бутстрап: при пустой базе первый проект создаётся из env
(`STATUS_API_URL`, `STATUS_API_TOKEN`, `GITHUB_REPOS`, `BOOTSTRAP_*`) —
чтобы существующая установка поднялась без ручного SQL. После этого env
не читается, источник истины — база.

## 3. Архитектура

```
 у нас (сервер Scalefield):
 браузер ──► панель (Next.js) ──► control-plane API ──► Postgres `scalefield`
                                        │  POST /servers/<id>/request
                                        ▼
                                      relay ◄──────────────────────────────┐
                                                                           │ исходящий WSS,
 у клиента (его VPS, за NAT/файрволом — не важно):                         │ входящих портов нет
                     сервер проекта: агент (FastAPI) ─┬─ docker.sock ──────┘
                                                      ├─ pg_stat_* базы проекта
                                                      └─ access-log Traefik
                     Traefik (edge, TLS) ── контейнеры сервисов ── Postgres ── R2
```

- **Control-plane** — единственный, знает всё о проектах, хранит секреты.
  Панель и API в одном Next-приложении (как Studio у Supabase). До агента
  достаёт через одну функцию — `agentRequest` (`src/lib/agent.ts`), всё
  остальное транспорт не различает.
- **Relay** — точка входа для агентов (`relay/`). Отдельный процесс, а не
  часть Next: WebSocket-сервер в Next standalone потребовал бы кастомного
  сервера, а так панель остаётся stateless. Relay не ходит в базу: чей
  токен — спрашивает у control-plane (`/api/internal/relay/auth`), туда же
  шлёт «подключился / heartbeat / отключился» (`servers.last_seen_at`,
  `agent_version`). Общий секрет `RELAY_SECRET` в обе стороны.
- **Агент** — один на сервер, ничего не решает сам: отдаёт метрики и
  исполняет команды деплоя. **Подключается сам** (`agent/app/tunnel.py`):
  держит исходящий WebSocket к relay, присланные запросы прогоняет через
  собственное FastAPI-приложение внутри процесса (`httpx.ASGITransport`), так
  что ручки `/status/*`, `/jobs/*`, `/deploy/*` не знают о туннеле. Обрыв —
  переподключение с backoff до 60 с. Это то, что позволяет ставить агента на
  чужой VPS за NAT и файрволом, не открывая порт с доступом к docker.sock.
  Переходный прямой режим (`servers.agent_url` задан → HTTP с
  `X-Status-Token`) остаётся, пока агент на Timeweb не обновлён, и уйдёт.
- **Билдер** — сборка образов вне сервера проекта (GitHub Actions сейчас,
  отдельный builder-хост потом): сервер на 2 ГБ сборку Next не тянет,
  и это останется правдой для клиентских VPS.
- **Edge** — Traefik на каждом сервере: домены и сертификаты решаются
  лейблами контейнеров, control-plane лишь генерирует compose.

Чего сознательно НЕ делаем: serverless-функций, edge-рантайма, своего CDN,
глобальной репликации. Это не наша весовая категория; наша — «свой VPS,
но с опытом Vercel/Supabase».

## Аналитика посетителей (26.09)

`/p/<slug>/analytics` получил раздел «Visitors» (в духе Vercel Analytics) над
существующим разделом Traffic: посетители (уникальные IP), просмотры страниц,
bounce rate — со сравнением с предыдущим таким же окном (7 дней по умолчанию),
посуточный график, топ страниц, источники перехода, устройства/браузеры/ОС.
Всё считается заново из того же JSON access-лога прокси, что и Traffic —
`agent/app/collectors/visitors.py` (переиспользует парсер `api_traffic.py`),
эндпоинт `/status/visitors?days=&hosts=`.

- «Просмотр страницы» — GET, статус < 400, путь не под `/api/`, `/_next/`,
  `/pdf/` и не статический файл, UA не похож на бота (обычный список ботов
  сканеров/краулеров/HTTP-клиентов, не только поисковики). Иначе боты и
  собственный API-трафик раздували бы цифры.
- Устройство/браузер/ОС — компактный классификатор по UA без внешней
  зависимости; незнакомое попадает в «Other», а не выдумывается.
- Источники перехода: Traefik на проде сегодня не пишет заголовок `Referer`
  в лог (только `User-Agent`), поэтому раздел честно показывает "capture
  isn't enabled" вместо того, чтобы называть весь трафик "Direct". Включить —
  один флаг `--accesslog.fields.headers.names.Referer=keep` в конфиге
  Traefik на сервере (не сделано намеренно — это правка боевого сервера,
  не только Scalefield).
- Страны — сознательно не делали: нужна GeoIP-база (MaxMind), это отдельная
  зависимость и лицензионный ключ; выдумывать разбивку по странам без неё
  хуже, чем не показывать раздел.
- Трафик на общем сервере режется по доменам проекта (`hosts=` из
  `services.domains`) — тот же принцип, что и у [[container-scope]] для
  контейнеров: без этого один проект видел бы посетителей другого.

## Клиентский трекер `<Analytics />` (26.09)

Второй, более точный источник для раздела Visitors: `scalefield-analytics.tsx`
(эталонный файл в корне репо, копируется в проект — Scalefield и отслеживаемый
сайт всегда разные деплои) шлёт маячок на `POST /api/collect` при каждом
переходе, включая клиентские SPA-переходы, которых разбор лога прокси не видит.
Площадка узнаётся по домену (`services.domains`), в компоненте нет ID проекта —
как у `@vercel/analytics`. `/api/projects/<slug>/analytics/visitors` предпочитает
эти данные (`page_views` в control-plane БД), если они есть, иначе честно падает
на старый `agent/status/visitors` (разбор лога) с пометкой источника в ответе.
Общий классификатор устройства/браузера/ОС — `src/lib/ua.ts` (TS) и
`agent/app/collectors/visitors.py` (Python) держать в синхроне вручную: логика
портирована 1:1, но это два разных языка, авто-синхронизации нет.

## Изоляция между проектами (25.09)

Агент отдаёт ВСЕ контейнеры своего хоста через docker.sock — на сервере с
несколькими проектами (или на машине разработчика) это чужие стеки. Как в
Vercel и Supabase, проект не должен видеть чужие ресурсы: `src/lib/container-scope.ts`
фильтрует список контейнеров на сервере (в прокси `/api/projects/<slug>/status/*`)
ДО того, как он уйдёт в браузер — по `services.container` (ручная привязка,
поле «Container name» в форме сервиса) или по конвенции агента-деплоя
`<project-slug>-<service>`. `container-logs?name=` дополнительно проверяет, что
запрошенный контейнер принадлежит проекту, — иначе с одной панели читались бы
логи чужого сервиса на общем сервере. Остальные разделы
тоже режутся по проекту (27.09, после того как у qrtifact в Database и
Overview показывалась база researcher.uz):
- `database`, база в `summary` — база ПРОЕКТА из `databases`: control-plane
  шлёт агенту её строку (`POST /status/database|summary`), агент держит пул
  на каждую строку (`agent/app/db.py`). Нет базы — `db_ok = null`
  («not connected») и форма «Connect database» (`PUT
  /api/projects/<slug>/database`, строка проверяется через агента до
  сохранения). База, прописанная агенту в env, для проектов больше не
  используется — только для метрик контента researcher.uz.
- `api`, `logs`, `visitors` — только запросы к доменам проекта (`hosts=`
  принудительно, `host` из UI — лишь среди них); без доменов — «не
  настроено», а не трафик всего сервера.
- `content` — метрики researcher.uz, включаются флагом `contentMetrics`.
- `server` (CPU/RAM/диск) — честно общие для хоста: это метрика сервера, а
  не проекта; при «один сервер = один клиент» совпадает с проектом.
Грабли: агенту нужен доступ в сеть базы каждого проекта (в compose прода
`status-api` в `backend_internal` и `qrtifact_internal`), а в нескольких
сетях имя `db` неоднозначно — базы адресуются именем контейнера
(`backend-db-1`, `qrtifact-db-1`).

## 5. Решения, которые не пересматриваем

- **Никаких мок-данных.** Если метрики нет — панель говорит «не настроено».
- **Образы не собираются на сервере проекта.**
- **Одна база control-plane, одна таблица деплоев** для всех источников.
- **Агент подключается сам, входящих портов у него нет.** Ни `curl | sh`, ни
  SSH-установка, ни API хостера не заработают за NAT, если панель должна
  достучаться до агента; и открытый порт с доступом к docker.sock — это root
  по сети. Поэтому обратный туннель — не оптимизация, а условие BYOC.
- **Сервер у клиента; один сервер = один клиент.** Изоляция между
  клиентами — граница VM, а не контейнера: выход из контейнера даёт root на
  хосте, и `container-scope.ts` остаётся UX-фильтром, не защитой. Когда
  появится режим «сервер за вас», он заказывает клиенту отдельную VM через
  API хостера, а не подселяет его на общий хост.
- **Код не обязан быть открытым.** У клиента стоит только агент; панель,
  control-plane, relay и биллинг — у нас (модель Forge, Datadog, GitHub
  runners). Открывать код или нет — бизнес-решение, архитектура одна.
- **Тяжёлое — за пределами сервера researcher.uz**: 2 vCPU / 2 ГБ, ML и
  сборки туда не ставить.
- **Стек не множим**: TypeScript для control-plane и панели, Python для
  агента (там живёт docker/psutil-код), Traefik для edge. Переписывать агент
  на Go имеет смысл только ради установки одним бинарником на чужие хосты.
